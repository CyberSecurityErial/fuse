# 当前反向 bench 的搜索方式

这是一套**全 shape、有限参数候选**的搜索，不是全参数穷举。
不能把“测完所有 shape”说成“已经找到所有参数的全局最优”。

## 固定的测试范围

QKV 和 OProj 两个反向算子，各自沿用旧 SM90 的 8 组模型形状。
每组测全局序列 1024、4096、16384、131072、262144、524288，以及 CP4、CP8。
合计 192 个配置。Batch 固定为 1，本卡 token 数等于全局序列长度除以 CP。

权重离线量化为 MXFP8，每 32 个原始输入轴元素共用一个 scale。
运行时先反量化成 BF16，再做 BF16 GEMM。激活和通信不量化。
新反向主表固定使用 FP32 的 dW/main_grad。

## 搜索哪些参数

1. **cuBLASLt 算法**：每个 GEMM 最多请求 32 个候选，库可能实际返回更少。
   每个候选预热 2 次，再连续运行 6 次，按平均耗时选择。
   输入梯度与权重梯度分别调；权重梯度的覆盖写入和累加写入分别调。
   每张卡独立选择算法，原始结果里的算法信息来自 rank0。
2. **NCCL 通信配置**：只试三套整组配置：默认；24 channels/128 KiB chunk/
   64 KiB LL threshold；32 channels/512 KiB chunk/64 KiB LL threshold。
   这里的 chunk 是 NVLink P2P 通信 chunk，不是序列长度。
   不把三列参数再做交叉组合。
3. **TE Userbuffers 通信 SM 数**：只试 4、8、16。
   当前固定最多 3 个发送 stream、push 模式、关闭 CE；没有搜索这些固定项。
   打包 kernel 固定 block=512、warps=4，没有搜索其组合。

## 怎么选、怎么复测

对每个 shape，通信候选先预热 3 次、采样 12 次。
每个样本先取所有 rank 的最大耗时，再算 p50。
Eager 和 CUDA Graph 分别选择输入梯度阶段最快的通信配置。
这里的输入梯度阶段在代码中叫 B，**B 不是 batch**。
它包含该算子的通信、打包/解包、权重反量化和 dX/dA GEMM。

普通模式和梯度累加模式共用同一输入梯度通信选择，因为权重梯度阶段没有通信。
当前不是按完整反向总耗时选择通信参数。
选好后，只对胜出配置重新预热 10 次、采样 50 次。
正式结果不复用短扫样本，分别记录输入梯度、权重梯度和顺序完整反向耗时。

## 为什么执行得比较快

一个分布式进程组连续处理多个 shape，不为每个样本或候选启动新进程。
NCCL 的三套环境配置分别用新进程，避免库缓存环境变量导致切换无效。
确定赢家后，把选择相同配置的 shape 放进同一个正式测试进程。
同一进程、同一 shape 内复用 GEMM 启动计划，TEUB 的通信 SM 候选共享这些计划。
NCCL 换环境配置会启动新进程，因此会重新建立并调优 GEMM 计划；正式复测的新
进程也会重新调优。不能声称跨进程复用了完全相同的 GEMM 算法。
内存分配、编译、算法搜索、图捕获和正确性检查都在正式计时之外。
跨 rank 的耗时向量在采样完成后一次收集，不在每个样本里做 GPU 归约。

这些措施减少测试框架开销，但不会减少正式 shape 或 50 次采样。
Eager 的 CUDA event 时间仍可能包含主机提交间隙，所以 Eager 与 Graph 分开报告。
实际候选定义见 `backward_suite.py`、`backward_bench.py` 和 `backward_gemm.cu`。
