# QKV Projection Backward Benchmark

## 口径

- BF16 QKV projection 反向，分别测数据梯度阶段 B 和权重梯度阶段 W；
- B 阶段先把各卡的 `dQ/dK/dV` 直接路由成目标卡自己的完整 `dQKV`，随后计算 `dX`；
- W 阶段使用 B 阶段得到的 `dQKV` 和前向输入 `X` 计算 `dWqkv`；
- 三个人工压力 shape 加五组真实 GQA 模型，六档全局序列长度，CP4/CP8，共 96 个 setting；
- 每个正式结果使用 10 次 warmup + 50 次采样；MPI 一进程一卡，每个样本先取跨 rank 最大延迟，再报告 p50/p95；
- Eager 与 CUDA Graph 分别采样、分别成列；Graph 的 capture、instantiate、upload 和 host launch 不计时；
- 吞吐同时计算 B 和 W 的 GEMM FLOPs，即总计 `4×M×hidden×QKV_width`。
- 经典 cuBLAS 使用相同的 B/W MNK 和真实零拷贝转置视图，分别测纯 GEMM；普通模式的 W 对照使用 `beta=0`，ZeroBubble 使用 `beta=1`，保证累加语义相同。它不包含 A2A，用来表示该 shape 在当前卡组上的计算上限。
- 每份 raw JSON 直接保存 B/W MNK、自动请求、最终通信 CTA、tile、beta 和 50 个 max-rank 样本；汇总表不靠模型名反推反向矩阵。

### 测试设备

CP4 固定使用物理卡 `0,2,4,5`，CP8 使用全部 8 张 132-SM H200 级 GPU。物理卡 `1,3,6` 的 SM 频率上限为 1500 MHz，其余为 1980 MHz；显存频率均为 3201 MHz。经典 cuBLAS 在本轮同一卡组上同步测量；“前向占比”使用仓库已发布的同 shape、同启动方式前向 Golden，作为统一的版本目标，不冒充同一时刻的成对 A/B。

## 反向 Shape 和顺序

前向权重按 `[QKV,H]` 保存，`QKV=(Hq+2×Hkv)×D`。反向的两个 GEMM 是：

```text
B: dX[M,H]       = dQKV[M,QKV] × Wqkv[QKV,H]
   GEMM MNK       = M × H × QKV

W: dWqkv[QKV,H]  = dQKVᵀ[QKV,M] × X[M,H]
   GEMM MNK       = QKV × H × M
```

这里 `M=B×S/CP`。B 阶段的通信顺序与前向相反：每个 source rank 持有所有 token、部分 head 的平面 `dQ/dK/dV`，通信 CTA 直接把它们写入每个 destination rank 的 `[M,QKV]` 缓冲区，列顺序固定为“全部 Q、全部 K、全部 V”。GEMM CTA 只在对应 head 块写完后读取，不需要框架先做 `cat`、`index_select`、`permute` 或 `contiguous`。

## 普通反向和 ZeroBubble

普通模式调用 `launch_qkv_backward()`，在同一 stream 中严格执行 B→W。W 不会在 B 的 `dQKV` 完整可见以前启动。

ZeroBubble 模式把两段拆开：调度器先调用 `launch_qkv_backward_data()`，在以后安排的 W 阶段调用 `launch_qkv_backward_weight()`。从 B 完成到 W 完成，目标卡的 `dQKV` 缓冲区和前向输入 `X` 都不能被覆盖；每个尚未完成的 B→W 间隔需要一个独立 slot。框架能保留这两个 slot 时无需额外 D2D copy；不能保留时，显式保存就是 ZeroBubble 必须承担的存储成本。

正式 ZeroBubble 表使用 `beta=1`，把本次 `dWqkv` 累加到已经存在的 BF16 `main_grad`；普通同流表使用 `beta=0`。多个 W 阶段不能在不同 stream 上同时写同一个 `main_grad`，调用方必须按参数串行化，或使用独立梯度槽后再归并。

## 自动策略

B 阶段的生产入口统一传 `comm_ctas=0` 和 `gemm_policy=auto`。策略只读取 M/N/K、CP、head geometry、SM 数、route task 数和合法 tile 几何；不读取模型名、TE 结果或逐 case winner。候选为 `M128N64`、`M128N64 cluster-M2`、`M128N128`、`M128N160`、`M128N192` 和 `M128N256 cluster-M2`。

第一次遇到某个设备和 shape 时，算子联合确定通信 CTA 和 GEMM tile；后续 Eager 调用直接复用这个只含整数配置的启动计划。数据地址、epoch、alpha 和输出地址仍逐次读取，不会被缓存。W 阶段使用独立的普通 CUTLASS Wgrad kernel，不占用通信 CTA。

正式 Graph 数据把 10 个预热 epoch 和 50 个正式 epoch 捕获成一条单调链，只 replay 一次。若框架要反复 replay 同一个 graph，必须在 replay 前统一重置跨卡状态，或更新 graph 中的 epoch；不能让旧 ready/done 值冒充新一轮完成。

## 正确性门槛

- 小矩阵 smoke 独立重建 rank-major 和 causal dual-chunk 布局，覆盖 CP4/CP8、普通 B→W、分离 B/W，以及 `beta=1` 梯度累加；
- 另有 CP4、batch=2、M=256 的 causal 用例，实际走 TMA 路径，验证 batch 偏移和双 chunk 映射；
- 正式 S=1K 的全部 QKV setting 在 host 端逐元素重建完整 inverse route，并检查 ready/done epoch、目标缓冲区、`dX` 和 `dW` 均被写入；
- 原有前向 QKV/OProj smoke 保持全通过；v9 的 43 个旧 device kernel 指令体与 v10 构建逐字一致，v10 只增加反向 kernel 实例。

## 复现

```bash
cmake -S . -B build-v10-release \
  -DCMAKE_BUILD_TYPE=Release -DFUSE_ENABLE_PROFILING=OFF
cmake --build build-v10-release --parallel 8 \
  --target backward_smoke backward_mpi_bench backward_cublas_mpi_bench

CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 ./build-v10-release/backward_smoke

python3 benchmarks/backward/backward_shape_bench.py \
  --phase formal --phase cublas --phase aggregate \
  --operators qkv --launches eager,graph \
  --weight-modes deferred,immediate \
  --seqs 1024,4096,16384,131072,262144,524288 \
  --cps 4,8 --warmup 10 --iterations 50 \
  --bench build-v10-release/backward_mpi_bench \
  --cublas-bench build-v10-release/backward_cublas_mpi_bench \
  --results results/QKVproj-backward/qkv_backward_shape_bench \
  --no-resume
```

runner 默认在同一次 MPI/CUDA 进程中依次完成四种启动/调度组合，以减少重复创建进程的时间。每种组合仍有独立的 10+50、独立的 CUDA events、独立 JSON 和独立缓冲区；这项编排不合并计时边界。
